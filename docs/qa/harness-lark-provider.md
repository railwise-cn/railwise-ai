# Typed Feishu/Lark execution boundary

The provider is an independent RailWise adapter around the official `larksuite/cli` executable managed by the main process. It never accepts arbitrary command lines, executable paths, shell fragments or API URLs from model arguments. DingTalk is a separate provider and is never routed to this adapter.

The CLI protocol was checked against upstream commit `1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a` on 2026-11-10:

- [Task list](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/skills/lark-task/references/lark-task-get-my-tasks.md): `task +get-my-tasks --complete=false`.
- [Task completion](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/shortcuts/task/task_complete.go): target GUID, nonzero completion time and `done` state.
- [Approval catalog](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/internal/registry/catalog/services/approval.json): task query, instance detail, approve/reject and exact scopes.
- [Authorization status](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/cmd/auth/status.go) and [device login](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/cmd/auth/login.go): structured identity and granted user scope parsing; no-wait/device-code flow.
- [First-time app setup](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/cmd/config/init.go) and [official app registration](https://github.com/larksuite/cli/blob/1bfdcc2c1a0ed0296ddb6349d251bdd75145bc5a/cmd/config/init_interactive.go): `config init` blocks while polling; it has no no-wait/device-code API. A managed original subprocess publishes the official scan URL and expires after 15 minutes. Cancellation targets that captured child only. The renderer never receives CLI stdout or application credentials.

The reusable connection panel in the connector catalog and task card separates installation, application setup, user authorization and task resume. Viewing the catalog reads local/runtime diagnostics under the configured credential-access policy; it does not install dependencies, start authorization or execute tasks. An explicit Connect action checks/installs the official CLI and opens the official scan page. Setup first checks `config show --json`; only the structured `config/not_configured` error permits initialization. Invalid configuration remains intact. Setup uses a unique `--name railwise-<UUID>` profile so it cannot replace an existing application profile through bare `--new`. User authorization updates the selected application's current account according to the official CLI; the UI discloses that account change and leaves platform permission confirmation to the user. Connecting never implicitly executes the queued task.

Each login flow binds its application/profile and executable hash, reuses an active device flow, and reports success only when that flow succeeds and a fresh user identity has every requested scope. An older valid login cannot hide device-flow failure or a partial grant. Identity fingerprints bind brand, application ID and user open ID; display names and access tokens are not identity keys. Official CLI profile selection is fixed by `--profile`; the upstream CLI has no `--user` flag and selects the profile's current user, so the implementation does not claim atomic protection against another process changing that user between separate CLI calls. Candidate mode uses the official `LARKSUITE_CLI_CONFIG_DIR` under the isolated candidate home without resetting system `HOME`; disabled candidate credential access blocks app setup, login, and account diagnosis.

`auth status` can exit zero with no usable user identity. Exit status alone is therefore insufficient. The adapter requires the diagnosed user identity, known Feishu/Lark brand and actual user scopes. Unknown/old CLI output fails closed and does not register tools. Existing user disables remain effective. Scope changes/removal clear stale capability state.

Writes always use the existing approval service even under the runtime `auto` policy. Approval cards contain the exact task/instance IDs. Only after approval does the provider add the CLI's required `--yes` flag. The model never receives credentials or the device code. The main process holds a single expiring device authorization, validates the official HTTPS verification URL, then persists a fresh diagnosed snapshot and requests a Runtime hot refresh without restarting active tasks.

Mutation success requires a target-specific observed remote state. Task completion checks the GUID and completion timestamp. Approval changes read the exact instance and compare the exact approval task status. Failed/absent readback produces `outcome_unknown`; it does not rerun the write. Persistent receipts retain bounded evidence metadata and redact remote form contents and comments.

Focused automated tests cover argument validation, scope filtering, explicit write denial, approval readback, wrong target, malformed responses, bot-only identity, private device-code flow, persisted evidence and capability refresh. These use synthetic fixtures. No live user account, real approval, or real todo mutation was executed during this implementation. Fixture tests are not substitutes for configured-account checks.
